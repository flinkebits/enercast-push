Overview

Authentication

Basic Auth

For testing the REST-endpoints of the API, standard Basic Auth is supported. This authentication method should never be used productively, as it is subject to strict rate limiting. Basic Auth works by providing the Authorization-header in a request in the form Basic <credentials> where <credentials> is the Base64-encoded representation of the username and password separated by a colon.

JWT based Auth

To access the API, a JWT-based token should be used. This token can be requested from the /v1/auth-endpoint. After retrieving this token, it can be used to authenticate against the API. This is done by providing the Authorization-header in the request in the form Bearer <token> where <token> is the previously obtained token.

Generated tokens currently have a lifetime of 1 hour. After expiry, a new token must be retrieved from /v1/auth.

General Definitions

Names

Strings used for names and identifiers can use the full UTF-8 character set. The length must not exceed 250 characters.

Number Formats

Numbers are decimal, using '.' (dot) as the decimal separator. Scientific format is supported.
Thousands separator must not be used.

Examples: 1.0234E3 or 1023.4

Date and Time Formatting

Date and time values in requests and responses follow the ISO 8601 and RFC 3339 standards. The supported format for UTC is: [YYYY]-[MM]-[DD]T[hh]:[mm]:[ss]Z

It is important to distinguish between two common representations of date and time:

  • Instant Represents a unique point in time, independent of time zones. Always expressed in UTC, with a trailing Z.
    Example: 2022-03-25T15:30:00Z

  • Local time Represents a date and time without time zone information and does not include a trailing Z. By itself, a local time cannot be mapped to a unique instant unless paired with a time zone. Example: 2022-03-25T17:30:00 (time-zone = Europe/Berlin)

Time Zones

All timestamps are stored and returned by the API in UTC. A time zone only comes into play when a request accepts a local time value (no offset/Z, e.g. ts.start, ts.end, ts.ref-ts) and you want to express it as local wall-clock time instead of converting to UTC yourself: the accompanying *.time-zone parameter (default UTC) tells the API which offset to apply before converting the value to UTC. The response is always returned in UTC, regardless of the requested time zone.

Time zone definitions must refer to the names from IANA tz data base.

Examples:

  • Europe/Berlin is the correct time zone for Germany.
  • Asia/Kolkata is the correct time zone for India.

In addition to names from the IANA tz database, the string UTC is also allowed.

Some time zones result in offsets from UTC by a fraction of an hour rather than a whole number of hours (e.g. Asia/Kolkata is UTC+5:30); this offset is applied the same way as for any other time zone when converting a local time to UTC.

Example: ts.start=2025-07-07T00:00:00 with ts.time-zone=Europe/Berlin is interpreted as 2025-07-06T22:00:00Z (CEST, UTC+2) - the exact offset depends on daylight saving time at that date.

Some request/response bodies (e.g. availability.time-zone) also carry a time-zone field; for reference to keep the information in which time zone the original entry was made which is helpful when entries are made for whole days in local time. It does not affect how the rest of that body is interpreted.

Time Intervals

ISO 8601 compliant notations for intervals, periods and points in time must be used.

Examples:

  • Single fully defined interval: 2019-02-08T02:45:00Z/2019-02-08T03:00:00Z

  • Point in time: 2019-02-08T02:45:00Z

  • Interval without defined end (e.g. start of a maintenance event with unknown duration): 2019-02-08T02:45:00Z/..

  • Interval without defined start (e.g. a planned delivery end): ../2019-02-08T02:45:00Z

Within all time series data structures, we consider a right open interval. This means that, for an interval from 2019-02-08T00:00:00Z to 2019-02-08T00:30:00Z, the point in time at 2019-02-08T00:30:00Z itself is not part of the interval. According to ISO 80000-2 (formerly ISO 31-11) this can be expressed as [,[ or [,).

Repetitive Intervals (e.g. Periods or Temporal Resolution)

For periods, a notation according to ISO 8601 recommendation is used, with an optional non-standard extension.

General Format: R{number of repetitions}/PT{number of time units}{M=minutes,H=hours}

Examples:

  • Period of 15 minutes repeated 96 times, e.g. a quarter-hourly forecast with a one-day horizon: R96/PT15M

  • Period of one hour with an undefined number of repetitions, e.g. a meter data stream with hourly temporal resolution: R/PT1H

When used as the temporal resolution attribute of a time series, the period is provided as an element of an array. This covers special cases with multiple concurrent period definitions. In these cases, the definitions are given as an array with elements separated by a comma.

Examples:

  • Time series containing quarter hourly resolution for the first day and hourly resolution at the second day: [R96/PT15M,R24/PT1H]

Time Series Format

A time series' format attribute selects one of two ways its values are exchanged:

  • Compact format (format: compact-values) Used whenever the resolution is constant across the whole series. Only start and the periodicity (see "Repetitive Intervals" above) are given once, together with a plain, ordered values array.

    Example:

    {
  "format": "compact-values",
  "quantity-name": "P",
  "unit": "W",
  "periodicity": ["R/PT15M"],
  "start": "2025-07-07T00:00:00Z",
  "interval-type": "[,[",
  "time-zone": "UTC",
  "instantaneous": false,
  "values": [0.0, 1000.0, 2000.0, 3000.0]
}

  • Explicit interval format (format: expanded-intervals-to-values) Used whenever the resolution is not constant across the whole series (e.g. a response spanning a change in temporal resolution). Each value is given together with its own explicit ISO 8601 interval as a map key.

    Example:

    {
  "format": "expanded-intervals-to-values",
  "quantity-name": "P",
  "unit": "W",
  "periodicity": [],
  "start": "2025-07-07T00:00:00Z",
  "interval-type": "[,[",
  "time-zone": "UTC",
  "intervals-to-values": {
    "2025-07-07T00:00:00Z/2025-07-07T00:15:00Z": 0.0,
    "2025-07-07T00:15:00Z/2025-07-07T00:30:00Z": 1000.0
  }
}

Physical Units

For all numerical values, the specification of units is mandatory.
Units are provided in a separate attribute and not as part of numerical values.

The list of supported units can be requested from the service endpoint /v1/static/supported-units.

Examples:

  • watt: W
  • kilowatt: kW
  • kilowatt-hour: kWh

Rated Power

The rated power of an accounts assets form the basis for accounting and billing. Refer to the up to date version of the Data Exchange Specifications available in the portal UI.

Endpoints

portfolios

A portfolio is a collection of assets, grouped and related in a hierarchical structure. At the portfolio level, this API manages the current draft revision's lifecycle. Editing operations (CRUD operations) on assets are managed with long running manual transactions. Any changes must be commited by an activate operation to become effective. This is the same behaviour as in the portal UI. Care must be taken when API and UI operations are done on the same account in parallel.

assets

Asset data management at the individual asset level is an alternative way to perform CRUD operations on assets. These endpoints provide read access to the latest productive version. Each change is written to a new draft portfolio revision (or an existing draft that has not yet been activated) - the draft is not activated automatically. Use the portfolio stage operations to activate or discard it.

availabilities

Availability management of an asset. Four types are supported:

  • Curtailment: limits generation to a given maximum.
  • Partial shutdown: scales generation down by a given percentage.
  • Shutdown: asset generates no power; forecast is also zero.
  • Forecast disabled: forecast is zero regardless of actual capacity or generation.

See the Availabilities table under "Data Stream Template Query Attributes" for the exact query parameters.
